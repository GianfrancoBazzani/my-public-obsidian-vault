# Exam Scenario F Notes

The company is a Full System according to the CCSS system typification. The firm offers custodial services to third parties so it controls customer funds.

## Aspect Control Requirements

### 1.01 Key Material Generation
- 1.01.1.1 L1 "Key material is generated by the actor who will be using it.": Not In Place (shares are "distributed in real time across multiple MPC nodes" — so the generating actor ≠ the using actor; key shares are key material per glossary, and one node is even operated by a third-party QSP. If the MPC scheme used distributed key generation (DKG) — each node generating its own share locally — this would be In Place; but the scenario never mentions DKG and says shares are "distributed" to the nodes, and unstated controls must not be assumed)
- 1.01.1.3 L2 "A digital signature for the key material generation mechanism is generated, published, and validated prior to each execution.": Not In Place (the requirement is about signing the generation *mechanism* not the key material. The scenario only mentions digital signatures on the encrypted backup shares; no evidence the generation mechanism's signature is generated, published, and validated before each execution)
- 1.01.1.2 L1 "Where an automated signing agent will use key material, and the place of generation of key material is different from the place of use. The following criteria are addressed: 1. The key material is generated within a secure Key Management System that meets applicable CCSS requirements. 2. The key material is transferred securely to the automated signing agent from the place of generation that meets applicable CCSS requirements. 3. The key material is securely removed from the place of generation that meets applicable CCSS requirements.": Not In Place (applies since shares are generated in one place and distributed to MPC nodes. Crit 1 only partially evidenced — Hash_DRBG 256-bit describes the algorithm, not the KMS security; Crit 2 not evidenced — no transfer mechanism described, and the QSP's L3 cert covers only its own node, not the exchange's distribution channel; Crit 3 not evidenced — no mention of secure removal of shares from the place of generation)
- 1.01.2.1 L2 "The methodology for generating key material is validated prior to use. Software does not include features that restrict which values can be used. Software does not include features that store or transmit data to another actor, unless that feature enhances security.": Not In Place (naming Hash_DRBG 256-bit is an algorithm choice, not evidence the methodology was *validated prior to use* — algorithm conformance is 1.01.3.1's job. No evidence about software features either: nothing on value restriction, and share distribution is transmission of key material with no assessment that it enhances security)
- 1.01.2.2 L2 "In cases where key material is generated without the use of software, the generation methodology is validated to ensure determinism is not present.": Not Applicable (requirement only applies to key material generated without software)
- 1.01.3.1 L3 "The generation mechanism for key material conforms to NIST SP 800-90A.": In Place (Hash_DRBG is one of the three DRBG mechanisms specified in NIST SP 800-90A, and 256 bits is an approved strength; the scenario states the mechanism explicitly)
- 1.01.3.2 L3 "The key material generation process has been documented and addresses the following: 1. The key material generation process must be conducted in a secure environment. 2. The physical environment that will be used for the key material generation process is checked before use for any unauthorised recording/surveillance equipment, windows allowing the key material generation process to be viewed by external personnel, poor physical separation of the area from the main working areas, effective physical access controls to restrict unauthorized access of personnel, backup power supply, environmental controls to protect against electromagnetic interference, sound leakage, or other vulnerabilities that could compromise the process. 3. All equipment and software used for the key material generation process must be checked before use for updates such as new software versions, any signs of tampering, and be in good working order. 4. All moveable equipment such as hardware devices, laptops, and key material is secured from unauthorized access when not in use. 5. A detailed runbook defines all steps performed during the key material generation process. After the completion of each step, the participating actors sign off in the runbook stating that the step was performed and checked. 6. All roles participating in the key material generation process must be defined and utilized. Segregation of duties must be considered when allocating personnel to roles. 7. Each actor involved in the key material generation process must independently generate their own discrete key material. In a multi-signer scheme, no single actor is permitted to generate key material that will be used by another actor unless the actor is an automated signing agent. (Refer to requirements 1.01.1.1 and 1.01.1.2.)": Not In Place (generic "key management" policy docs exist, but none of the 7 criteria are evidenced) 
- 1.01.4.1 L1 "Key material is generated on a Key Management System with sufficient entropy to ensure key material is not generated with any bias towards a reduced range of values, or other deterministic properties.": Not In Place (this requirement is about the KMS's *entropy*, not the algorithm — a Hash_DRBG is deterministic, so its output quality depends entirely on the entropy source that seeds it, and the scenario never mentions the seed source. Naming an 800-90A mechanism is 1.01.3.1's evidence, not entropy evidence; the testing procedure checks that "the entropy sources comply", consulting NIST 800-90B)

### 1.02 Wallet Generation
- 1.02.1.1 L2 "When considering the application of a single-signer mechanism to a wallet, the following criteria are addressed: 1. The criticality of the wallet to the CCSS Trusted Environment. 2. The impact of loss of customer funds controlled by the wallet. 3. The risk of a wallet compromise is included in the threat model defined in requirement 2.03.2.1. 4. The effectiveness of the security controls implemented to protect the wallet.": Not Applicable (requirement only triggers when a single-signer mechanism, the only wallet described is the 4-of-7 MPC threshold scheme)
- 1.02.2.1 L2 "A wallet that has implemented a multi-signer mechanism has at least one redundant key for recovery purposes.": In Place (the 4-of-7 threshold itself provides 3 redundant shares)
- 1.02.3.1 L2 "Key materials for a wallet that implements a multi-signer mechanism are stored in different locations.": Not In Place ("multiple MPC nodes" is a logical topology, not evidence of physically distinct locations — nodes could be co-located in one data center.)
- 1.02.4.1 L3 "Key material for a wallet that implements a multi-signer mechanism is stored by distinct operators within the entity or separate entities.": Not In Place (only 1 of 7 shares is evidenced under a separate entity — the QSP node. No operators are named for the other 6 nodes; "multiple MPC nodes" doesn't mean multiple operator)
- 1.02.5.1 L2 "The entity has a documented policy in place which details the company's internal policies and procedures and covers the relevant areas of wallet generation.": Not In Place (the scenario enumerates the policy set — "governance, key management, smart contract deployment, incident response, and vendor oversight" — and wallet generation is absent; a key management policy doesn't automatically cover wallet generation, which CCSS treats as its own aspect)

### 1.03 Key Material Storage
- 1.03.1.1 L1 "Key material is stored with the use of strong encryption when not in use.": Not In Place (the encryption evidence only covers the *backup* shares on the HSM — nothing states the operational shares on the exchange's own MPC nodes are encrypted at rest. The QSP node's share (1 of 7) can be relied on via its CCSS Level 3 certification, but the remaining 6 shares are unevidenced. Also, SHA-256 is a hash, not encryption — it provides integrity, not confidentiality, so it can never satisfy "strong encryption")
- 1.03.2.1 L1 "A backup(s) of the operational key material exists.": In Place (the scenario directly states "Encrypted backup shares)
- 1.03.2.2 L2 "A backup(s) exists for all key material used in the wallet. The backup can take any form (e.g., paper, digital, metal).": Not In Place (the requirement demands a backup for *all* key material used in the wallet, but "encrypted backup shares" is an unquantified plural — it evidences that backups exist (1.03.2.1's job), not that all 7 shares are covered, and unstated coverage must not be assumed)
- 1.03.3.1 L1 "The backup(s) is protected against environmental risks.": Not In Place (the backup is in an "access-controlled vault" — everything stated is access control, integrity, or monitoring; nothing addresses environmental risks like fire, flood, humidity, or electromagnetic damage)
- 1.03.3.2 L2 "The backup(s) of key material is stored in a geographically separate location(s) from the storage and usage of operational key material.": Not In Place (same gap as 1.02.3.1: the scenario gives no geographic information for either endpoint)
- 1.03.4.1 L1 "The backup(s) is protected by access controls that prevent unauthorized parties from accessing it.": In Place (explicitly stated: backups are "on an HSM within an access-controlled vault" — layered access control (HSM + physical vault), reinforced by secure logging, monitored audit logs, and quarterly inspections)
- 1.03.5.1 L2 "The backup(s) implements some form of tamper-evident mechanism that allows an operator to determine if it has been accessed.": In Place (for *electronic* backups the testing procedure looks for a mechanism that monitors/alerts on access — the scenario states secure logging on the backup shares, continuously monitored audit logs, SOC alerts on unexpected key access attempts, plus quarterly inspections using digital signatures/hashes to confirm no alteration. "Some form" is permissive and these stated mechanisms satisfy it)
- 1.03.6.1 L3 "Backups of key material are stored with the use of strong encryption that is equal or greater to the security prescribed for the operational key material.": Not In Place ("strong encryption" is an absolute demand, not just a comparison — even with operational keys unencrypted, backups independently need strong encryption. The scenario only says "Encrypted backup shares" with no algorithm/strength, and SHA-256 is a hash, not encryption)

### 1.04 Key Material Access
- 1.04.1.1 L1 "The entity maintains checklists that cover all tasks that are completed when personnel vacate or transition into key holder roles within the entity. These checklists have been reviewed by knowledgeable personnel to ensure 'least privilege principles' are applied to the system, as well as necessary access where required.": Not In Place (no checklists, onboarding/offboarding, or role-transition procedures are mentioned anywhere)
- 1.04.2.1 L2 "All key holder grant/revoke requests are conducted over Approved Communication Channels.": Not In Place (ACCs appear in the scenario only as part of key holders' general responsibilities and the KCP's compromise-response process — never tied to key holder grant/revoke requests; no grant/revoke process is described at all, so its channel can't be evidenced)
- 1.04.3.1 L3 "The entity's checklists include auditing information that record the identity of personnel that perform the grant/revoke operations. Each entry within the audit trail is attested to by personnel who performed that task.": Not In Place (follows from 1.04.1.1 and 1.04.2.1: no checklists and no grant/revoke process are evidenced, so audit info and attestations within them can't exist)

### 1.05 Key Material Usage
- 1.05.1.1 L1 "Access to the operational key material requires an identifier and at least 2 (two) distinct types of authentication factors.": Not In Place (no authentication mechanism for operational key material is described at all)
- 1.05.1.2 L3 "Access to the operational key material requires an identifier (e.g., username, email, GUID) and at least 3 (three) distinct types of authentication factors.": Not In Place (fails a fortiori from 1.05.1.1)
- 1.05.2.1 L1 "Key material is only used within the CCSS Trusted Environment.": Not In Place (concluding In Place because "no usage outside the system boundary appears in the scenario" would be an argument from silence — absence of counter-evidence is not evidence of the control. The scenario never delineates a Trusted Environment boundary, and nothing the testing procedure looks for — a policy requiring TE-only usage, generation records, key inventory, KMS inspection — is described)
- 1.05.2.2 L1 "The key material is isolated from other operating systems and application processes to avoid unauthorized access or leakage of key material.": Not In Place (the HSM holds the *backup* shares, not the operational ones — same conflation trap as 1.03.1.1. No isolation is described for the operational shares on the 6 exchange-operated MPC nodes: no HSM/enclave/dedicated hardware, nothing separating shares from other OS or application processes. QSP L3 reliance covers only its 1 of 7 shares)
- 1.05.3.1 L1 "All individual actors involved in operations with key material, or with the ability to impact the security of key generation, management, or usage have had their references checked prior to the actor being trusted with access to key material or operations.": Not In Place (no reference checks are mentioned anywhere; key holders being "internal executives" is not vetting evidence, and the required prior-to-trust timing is also unstated)
- 1.05.4.1 L1 "All individual actors involved in operations with key material, or with the ability to impact the security of key generation, management, usage, or storage have undergone identity verification to ensure they are who they say they are. These checks are conducted prior to the actor being trusted with access to key material.": Not In Place (no identity verification process is mentioned for any actor with key material access or security impact)
- 1.05.5.1 L1 "All individual actors involved in operations with key material, or with the ability to impact the security of key generation, management, usage, or storage have had background checks performed by law enforcement personnel or investigative firms. These checks are conducted prior to the actor being trusted with access to key material or operations and periodically; as allowed by local laws and regulations.": Not In Place (no background checks by law enforcement or investigative firms are mentioned, neither prior to trust nor periodically)
- 1.05.6.1 L1 "All individuals involved in key management operations, or with the ability to impact the security of key material, complete specific applicable training. This training is to be conducted on hire, and conducted before the actor being trusted with access to Key Material, and then annually.": Not In Place (no key-management training program is mentioned) 
- 1.05.7.1 L1 "Key management roles and responsibilities are formally acknowledged in writing by each person who has access to key material. This includes personnel who have been delegated key management responsibilities.": Not In Place (key holders *verbally* describe clear responsibilities in interviews — not a written acknowledgment. The "read and acknowledged by all staff" sentence attaches to the sanitization policy docs (1.06.1.1 territory), not to key management roles. And the electronic signatures on policies are by *a senior executive* — the document owner — not by each key holder)
- 1.05.8.1 L2 "Verification of fund destinations and amounts is performed via Approved Communication Channels prior to the use of key material.": Not In Place (the multi-party review/sign-off for settlement and vault pools never states that destinations and amounts are what gets verified)
- 1.05.9.1 L1 "Key material for a wallet that implements a multi-signer mechanism is stored and used on different logical or physical devices.": In Place (the scenario states shares are "distributed in real time across multiple MPC nodes" — nodes are distinct devices, logical at minimum, and "logical OR physical" is permissive)
- 1.05.10.1 L1 "Digital signatures follow best practices for the algorithm(s) implemented by the Key Management System.": Not In Place (the signature algorithm isn't even named)

### 1.06 Data Sanitization Documentation
- 1.06.1.1 L1 "Policy and procedure document(s) exist that conform to NIST SP 800-88 by defining the requirements for sanitizing and the destruction of media that holds key material. The policy and procedure documentation is read/understood by all staff who have access to key material.": Not In Place ("SP 227-B7" is not a real NIST publication the required benchmark is NIST SP 800-88, so the conformance leg fails outright. The read/acknowledged-by-staff leg IS satisfied nearly word-for-word, but one failed leg fails the requirement)
- 1.06.2.1 L3 "An audit trail is maintained for every piece of sanitized media conforming to the NIST SP 800-88 recommendation. These audit documents identify personnel who performed the sanitization, the specific identifiers of the media that was sanitized, which tool and configuration was used to perform the sanitization, and all other relevant pertinent information.": Not In Place (no sanitization audit trail of any kind is described)

### 2.01 Security Tests/ Audits
- 2.01.1.1 L1 "An individual(s) with expertise in information security must be engaged in all stages of the design, development, deployment, and ongoing maintenance of systems providing cryptocurrency functions.": Not In Place (Nothing shows infosec expertise engaged in *design* or *development* of the entity's systems. Note the expert need not be internal, but point-in-time external audits ≠ engagement in all stages)
- 2.01.1.2 L2 "A regular security assessment that includes vulnerability and penetration testing has been completed by an independent, qualified third-party. Documentation shows that all concerns raised by the assessment have been evaluated for risk and addressed by the entity.": Not In Place (annual testing and remediation tracking are stated, but the performer is not — no evidence it's an independent, qualified third-party; the third-party mention applies to the smart contract audits, not this testing)
- 2.01.1.3 L3 "A regular security audit at a level similar to SOC 2, ISAE3402, or ISO/IEC 27001, that includes vulnerability, penetration testing, and code audit (if applicable) has been completed by an independent qualified third-party. Documentation shows that all concerns raised by the audit have been evaluated for risk, addressed by the entity, and known vulnerabilities have been removed from the CCSS Trusted Environment. Ongoing audits are scheduled on a (minimum) yearly basis.": Not In Place (not enough evidence specified in the scenario)
- 2.01.2.1 L1 "All smart contract software code versions deployed to the environment(s) where the entity stakeholders interact with the smart contract have been audited by an external third-party auditor skilled in the development languages used for the smart contract software. NOTE: the requirement is not applicable to any environments used for development, testing, or staging. This requirement applies to smart contracts deployed to the 'production' network or the like.": In Place ("every contract is subject to a third-party audit and code review prior to deployment", with reports stored alongside deployment records — coverage, external auditor, and pre-deployment timing all stated. Caveat: "skilled in the development languages" is implicit; a real audit would verify the auditor's qualifications)
- 2.01.2.2 L1 "All smart contract software code audit reports are accessible to the entity stakeholders. The audit reports cover the currently deployed versions to the environment(s) where the entity stakeholders interact with the smart contract. NOTE: the requirement is not applicable to any environments used for development, testing, or staging. This requirement applies to smart contracts deployed to the 'production' network or the like.": Not In Place (reports are "stored alongside deployment records" — internal record-keeping, not evidence they are accessible to entity stakeholders such as the institutional clients interacting with the contracts)
- 2.01.2.3 L1 "All issues with a severity of medium or higher identified in a code audit of the smart contract software are addressed by the entity before deployment to the environment(s) where the entity stakeholders interact with the smart contract. NOTE: the requirement is not applicable to any environments used for development, testing, or staging. This requirement applies to smart contracts deployed to the 'production' network or the like.": Not In Place (findings are "tracked through a remediation system until all issues are confirmed as resolved" — eventual resolution, with no statement that deployment is gated on resolving medium+ issues first; the audits are pre-deployment but the remediation timing is not)

### 2.02 Log and Monitor
- 2.02.1.1 L1 "Audit trails exist for a subset of actions performed within the CCSS Trusted Environment.": In Place (the requirement only asks for a subset of actions, and the scenario states audit logs exist and are monitored — key/backup operations, SOC centralized logs)
- 2.02.1.2 L2 "All actions performed by all users within the CCSS Trusted Environment are logged. Audit logs are retained for at least one year in a trusted environment.": Not In Place (two gaps: the stated logging covers specific things — key access, trading anomalies — which is 2.02.1.1's "subset", with no claim of *all* actions by *all* users; and no retention period is ever stated, let alone one year)
- 2.02.2.1 L2 "In addition to recording all actions performed within the CCSS Trusted Environment, this audit information is periodically backed up to a separate server.": Not In Place (the backup leg IS stated — logs "backed up in near-real time to separate secure environments" — but the requirement presupposes recording of *all* actions, which is unevidenced per 2.02.1.2)
- 2.02.2.2 L3 "In addition to recording all actions performed within the CCSS Trusted Environment, this audit information is continually backed up to a separate server.": Not In Place (same as 2.02.2.1 — "near-real time" backup would even satisfy "continually", but the all-actions recording premise is unevidenced per 2.02.1.2)
- 2.02.3.1 L1 "The CCSS Trusted Environment's audit logs are monitored for suspicious activity, and alerts are generated when suspicious activity is detected. Appropriate personnel address the alerts generated. The monitoring frequency is defined by the entity and meets all components of requirement 2.03.2.1.": Not In Place (monitoring, alerting, and escalation are all stated, but the third leg requires the monitoring frequency to be derived from the threat model per 2.03.2.1 — and per my 2.03.2.1 finding, nothing states the threat model specifies task frequencies, so this leg fails too)
- 2.02.3.2 L2 "The CCSS Trusted Environment's audit logs are continuously monitored for suspicious activity, and alerts are generated in real time when suspicious activity is detected. Appropriate personnel address the alerts generated.": Not In Place (continuous monitoring and alert-handling are stated, but *real-time alert generation* — the qualifier that distinguishes this L2 from 2.02.3.1 — is not; the only "real time" wording in the scenario attaches to the log backups, not the alerting)
- 2.02.4.1 L3 "Relevant blockchain state (confirmed and unconfirmed) as it relates to the CCSS Trusted Environment are continuously monitored for anomalous behavior, generating alerts. Appropriate personnel address the alerts that are generated.": Not In Place (the continuous smart contract monitoring service is scoped to the smart contract program, not the TE's custody wallets; *unconfirmed* state / mempool monitoring is never mentioned)

### 2.03 Governance and Risk
- 2.03.1.1 L1 "A member of executive management is responsible for the security of the system and formally acknowledges their responsibilities in writing.": Not In Place (no executive is identified as responsible for system security. The senior executive's electronic signature on each policy is document approval — a distractor — not a written acknowledgment of personal responsibility for the system's security)
- 2.03.2.1 L1 "The entity has identified security threats to the CCSS Trusted Environment and have defined and implemented controls to reduce the residual risk of an attack to an acceptable level using a threat model. The following considerations are addressed: 1. The entity reviews the threat model periodically to ensure it is up-to-date, the controls currently implemented are still effective, and the risk of an attack is reduced. 2. If a procedure requires a defined frequency to perform tasks for a control, such as reviewing audit logs, the threat model specifies the task frequency.": Not In Place (nothing states the threat model specifies task frequencies — component 2 fails. The two-year review cadence is also questionable: CCSS sets no number for "periodically", but every cadence it does pin is at least annual)
- 2.03.2.2 L2 "The entity implements a risk management program based on industry recognized risk management standards and frameworks such as ISO/IEC 27005 and NIST SP 800-37.": In Place (explicitly stated: the threat model is "aligned with ISO/IEC 27005" — a named framework in the requirement — and the program is operational: risk treatment plans tracked with assigned owners and scheduled verification; the ISO 27001 certification corroborates)
- 2.03.3.1 L1 "Service provider management is implemented for any vendor or service provider that could impact the security of the CCSS Trusted Environment and addresses: 1. Procurement processes to ensure any vendor or service provider meets applicable CCSS requirements before contractual engagement. 2. Annual review of the vendor or service provider's compliance with applicable CCSS requirements. The frequency of review may increase from at least annually based on the entity threat model as defined in requirement 2.03.2.1.": Not In Place (vendors impacting the TE exist — QSP node operator, smart contract monitoring service — but no procurement process or annual compliance review is described for any of them; the QSP's L3 cert at engagement doesn't discharge the entity's *annual review* obligation. "Vendor oversight" in the policy list is a title, not evidence of the two components)

### 2.04 Key Compromise Documentation
- 2.04.1.1 L1 "An inventory of all key material exists and the entity has an awareness of which key material is critical to the successful operation of the CCSS Trusted Environment.": Not In Place (no key material inventory is mentioned; the quarterly backup-share inspection is an integrity check, not an inventory, and the tiered pool model shows criticality thinking about funds, not about key material)
- 2.04.1.3 L2 "The key material inventory is reviewed at least annually to ensure that all key material has been recorded and that the recorded information for key material is accurate and up-to-date.": Not In Place (follows from 2.04.1.1 — no inventory is evidenced, so its annual review can't be either; the quarterly backup-share inspection verifies the shares' integrity, not an inventory's completeness and accuracy)
- 2.04.1.2 L1 "A Key Compromise Policy and procedures are documented. The following is addressed: 1. Each specific classification of key material used throughout the CCSS Trusted Environment. 2. A detailed plan of dealing with its compromise that includes the use of Approved Communication Channels during execution. 3. Identities of actors via roles (not names), and includes secondary actors in the event any primary actor is unavailable to carry out the KCP.": Not In Place (the KCP exists and "outlines these roles" — component 3's first half — but key material classifications (1), a detailed compromise plan with ACC use (2), and secondary actors (3) are all unstated; a contents-list requirement fails when the contents aren't evidenced)
- 2.04.2.1 L3 "The Key Compromise Policy and procedures are tested at least annually to ensure their viability and to ensure personnel remain trained to use them in the event of a compromise. The following is addressed: 1. The testing exercise is documented and includes the attendees, scenarios tested, outcomes of testing, remediation required, actions, and the next testing date. 2. Any improvements identified from the test are updated in the Key Compromise Policy and procedures. 3. The testing includes ensuring backup(s) containing key material are reviewed and tested where applicable. 4. Any changes to the system's people, processes, and technology components trigger a test of the Key Compromise Policy and procedures.": Not In Place (annual drills happen and are documented with attendance logs — the headline is met — but the four criteria are mostly unevidenced: documentation contents beyond attendees (scenarios, outcomes, remediation, next date), improvements fed back into the KCP, backup testing within the exercise, and change-triggered tests are all unstated)
